System 1 Workbench (chat UI): developer README

The UI is generic: any model in the registry (shipped, trained on the Train tab, or post-trained) can be selected from the sidebar, and the verdict chips, flag form and Classes tab follow the selected checkpoint. The regulatory regime screener is the worked example that ships with it. A chat front end with two conversation sources: a scripted transcript replayed turn by turn (the default, for demos: no LLM or API key needed), or a live LLM (Claude via the Anthropic SDK, or any OpenAI-compatible endpoint). Every turn is screened by the regime classifier, and users can flag false positives and false negatives, which are written to a file.

1. Run it

# from the repo root, after the setup in docs/developer_guide.html
.venv/bin/python -m uvicorn app.server:app --port 8710
open http://localhost:8710

The default preset is Scripted transcript (demo, no LLM). It loads app/static/transcripts/demo_conversations.json (14 conversations written by Claude Fable 5.1 to exercise every regime on both speaker sides, plus clean ones), shows a conversation picker, and replays each exchange through the screening pipeline with Play next exchange / Play all. Each verdict also shows what the transcript's author expected for that turn ("expected Reg BI: agrees", "expected nothing, model said FINRA 2210", or "out of scope for this model" for S-P / S-ID under the 5-way checkpoint), so the demo can discuss hits and misses.

Upload your own transcript with the file control in the sidebar; the file is parsed in the browser, never stored on the server. Format: app/transcripts/FORMAT.md (JSON, conversations of alternating user/assistant turns, optional per-turn expected label and note).

"The classes" tab (top of the chat area) draws a diagram of the label space from the loaded checkpoint: the speaker split, each regime with its one-line trigger, the negative class, and any out-of-scope regimes greyed out (Reg S-P / S-ID under the 5-way model). It is generated in app.js (renderAbout) from /api/config, so it stays correct when the checkpoint changes; the trigger text lives in CLASS_INFO. The server also mounts docs/ at /docs so the tab can link to the architecture page.

For a live model instead, pick an Anthropic preset (needs ANTHROPIC_API_KEY or a key typed in the sidebar) or an OpenAI-compatible one.

No LLM handy? Run the offline mock and choose an OpenAI-compatible preset with base URL http://localhost:8799/v1:

.venv/bin/python -m uvicorn app.mock_llm:app --port 8799
# message containing "guarantee" -> FINRA 2210-style reply; "recommend" -> Reg BI-style reply

The first message loads Qwen3-8B (~15–20 s, ~16 GB). Press Load in the sidebar to warm it up first.

Which model: classifier.checkpoint in config.yaml. Default is the 5-way clm_regime_5way.pt (no flag + FINRA 2210, Reg BI, FINRA 4530, SEC 17a-3/4; privacy and identity-theft content is not flagged). Point it at clm_regime_7way.pt to also flag Reg S-P and Reg S-ID. The UI reads the class list from the checkpoint (/api/config → labels, unit_classes), so the verdict chips, the flag form and the scope note adapt automatically.

1. Where data comes from

Every file picker in the UI lists the data already in the project (GET /api/files), grouped by folder: data/ (your files; empty by default), app/examples/, app/static/transcripts/, datasets curated on tab 0 (app/data/curation/), and the regulatory example's splits under regime_clf/. Selecting one loads it server-side (POST /api/train/use_project_file, GET /api/files/transcript); paths are resolved and must sit inside one of those folders. A sibling <name>.spec.json prefills the class table. "Upload from your computer" remains as a fallback (browsers cannot point a file dialog at a folder). Files named *.private.* are gitignored.

1a. Data curation tab (step 0)

Runs the Claude Code CLI headlessly on the server to research a topic and write a labelled dataset from a prompt. Each run gets its own folder app/data/curation/<job>/; Claude Code is given a fixed output contract (dataset.jsonl rows of text / label / speaker / source / rationale, classes.json with one description per class and exactly one negative class, NOTES.md with sources and judgement calls). Tools are limited to WebSearch, WebFetch, Read, Write, Edit, Glob and Grep (no shell), the permission mode is acceptEdits so writes outside the job folder are refused, MCP servers are not loaded (--strict-mcp-config), and each run has a turn limit and a dollar cap (--max-budget-usd). The tab streams a live activity feed, validates what was written, supports follow-up prompts that resume the same session in the same folder, and Send to Train stages the dataset on the Train tab with the class table prefilled.

Setup. The CLI is auto-detected (CLAUDE_CODE_BIN, curation.claude_bin in config.yaml, claude on PATH, then the newest copy bundled with the Claude desktop app). It must be logged in for the server's user: run claude /login once in a terminal (or start the server with ANTHROPIC_API_KEY). The tab shows the exact command when it is not. Offline testing: CLAUDE_CODE_BIN=app/mock_claude_code.py (launch config chat-ui-mock-curation) emits the same event stream and writes a small sentiment dataset.

Caution. Claude Code reads web pages, which can contain instructions aimed at it; the tool restrictions above limit what such text could make it do, and every dataset is reviewed in the tab before it is used. Runs spend your Claude account or API credits.

1b. Train and Post-train tabs

Train builds a fresh model from an uploaded dataset in five gated steps: upload (CSV/JSONL with text, label, optional speaker and split) → define the classes (display name, the description the model scores against, which speaker can trigger it, and which class is the negative / nothing-to-flag class; exactly one is required) → validate (unknown labels, tiny classes, duplicates and conflicting labels, blocked real-firm names (scrubbed), speaker/label consistency, imbalance, stratified 80/10/10 split when none is given) → train (epochs, learning rate, initialise from the reference CLM heads or the active model; runs as a background job with progress) → results (accuracy / precision / recall / F1 for the model, a linear-probe baseline and the zero-shot reference heads, confusion matrix, per-class table, a link to the generated Tests/<date>_ui_<name>/report.html, and Activate).

Post-train continues the active model's heads on its original training data plus expert corrections: the false-positive / false-negative flags raised in the chat (app/data/feedback.jsonl, latest flag per turn wins, labels outside the model are skipped) and optionally an uploaded file of expert rows using the model's own labels. Expert rows are split 80/20 train/val and the train part is oversampled (default ×5). The candidate is then gated against the active model on the job's held-out split and, when the label space is a subset of the shipped taxonomy, on both OOD sets: any macro-F1 drop over 0.01 or per-class recall drop over 0.05 is a regression. Promotion is one click when the gate passes and requires a typed reason otherwise (logged to app/data/promotions.jsonl). The registry (app/data/models.json) lists every checkpoint with its metrics and gate result; any entry can be activated.

Example data. app/examples/ ships regime_5way_sample.csv and regime_7way_sample.csv (with .spec.json files that prefill the class table) and regime_5way_expert_corrections.csv for the post-training step; both tabs list them in a dropdown (GET /api/train/examples, POST /api/train/use_example). Add your own by dropping a CSV/JSONL (and optionally a <name>.spec.json) in that folder.

Versioning. Every trained checkpoint gets a registry entry with base_name, version (the first model called X is v1, later ones X_v2, X_v3, …), parent (the checkpoint it was initialised from), metrics, gate result and the training-data path. Activations are appended to app/data/promotions.jsonl.

Mechanics: app/training.py (uploads, validation, job thread, gate, registry) and regime_clf/train_api.py (the training recipe with classes passed as data). Embedding uses the encoder the screener already holds, through the shared emb_cache/ store, so texts seen before are free and no second Qwen3-8B is loaded. One job runs at a time. Activation hot-swaps the heads; the encoder stays loaded.

2. What happens on a turn

  1. The browser posts /api/chat with the provider settings, the visible history and the new message. In replay mode it also sends scripted_reply (the transcript's assistant turn) and the expected labels.
  2. The server screens the user message with the client-side regimes.
  3. The server calls the selected LLM through app/llm.py; with provider scripted it uses scripted_reply instead (an empty reply means the conversation ended on a user turn, and only that turn is screened).
  4. The server screens the reply with the assistant-side regimes (2210, Reg BI, compliant).
  5. The turn (both texts, both verdicts, latencies) is appended to app/data/turns.jsonl, and the JSON goes back to the UI.
  6. Each bubble shows a verdict chip, a details toggle with all class probabilities, and a flag link: Flag false positive on flagged text, or Flag false negative on clean text. The flag form asks for the correct label and an optional note, then posts /api/feedback.

With screening.on_flagged_response: withhold in config.yaml, flagged replies are hidden behind a “Show anyway” control instead of being shown with a warning chip.

5. Common changes

Add an LLM provider

Most endpoints are OpenAI-compatible: add a preset to config.yaml and you're done. For a different wire format, add a branch in llm.chat() and a function returning the reply text; raise LLMError with a human-readable message on failure. For Claude, always go through the anthropic SDK.

Change what gets screened

Speaker-to-class masks live in regime_clf/inference.py (UNIT_CLASSES, filtered to the checkpoint's classes at load time); the flag form takes them from /api/config, so there is nothing to keep in sync. Set screening.unit_masking: false to score all seven classes for both speakers.

Use a GPU encoder

Set classifier.emb_url to a vLLM pooling server (vllm serve Qwen/Qwen3-8B --runner pooling --port 8090). The server then loads only the 75 MB heads.

6. Security notes

  • API keys are never written by the server. Keys typed into the UI live in that tab's sessionStorage and travel with each request to your own server only.
  • There is no authentication. Bind to 127.0.0.1 (uvicorn's default) or put it behind your SSO proxy before sharing.
  • turns.jsonl contains raw chat text, so treat it as sensitive data (rotation and retention are on the improvements list).

7. Testing checklist

  1. Start the server; with the default scripted preset, pick a conversation and Play all; every turn should get a verdict and an "expected …" line, and a flagged assistant turn should show the warning chip.
  2. Upload app/static/transcripts/demo_conversations.json through the file control; the picker should repopulate. Upload a malformed file; the info line should show a readable error.
  3. Start mock_llm; select an OpenAI-compatible preset with the mock URL.
  4. Send “My advisor sold my bonds without asking. Can you guarantee my new fund won't lose money?”; expect the user message → FINRA 4530 and the reply → FINRA 2210.
  5. With the 5-way checkpoint, send “Here is my SSN 000-12-3456 for the form.”; expect No flag (out of class). With the 7-way checkpoint, expect Reg S-P.
  6. Flag the reply as a false positive; check that app/data/feedback.jsonl gains a row with kind: false_positive.
  7. Send a neutral question, then flag it as a false negative with a chosen label.
  8. Switch to an Anthropic preset (with a key set) and repeat step 2 against a live model.
